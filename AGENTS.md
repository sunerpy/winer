# AGENTS.md — winer

Project-specific agent instructions. The global instructions also apply; this file adds what only
matters here. The layout is in `README.md`, the design system in `DESIGN.md`, measured client and
host facts in `docs/platform-notes.md`.

## Baseline commands

```bash
cargo test --workspace        # lcu 12, winer (shell) 39, winer-core 280 — all pass
pnpm test                     # shared 7, plugin 71, desktop 130 — all pass
cargo clippy --workspace --all-targets -- -D warnings
pnpm lint && pnpm typecheck && pnpm format:check && cargo fmt --all --check
scripts/evidence.sh           # all of the above plus the Windows check, logged with the tree's hash
```

- `packages/shared/src/bindings.ts` is generated by `ts-rs`. After changing a type in
  `crates/core/src/view.rs`, `settings.rs` or `plugin.rs`, run
  `UPDATE_BINDINGS=1 cargo test -p winer-core bindings`; a new type must also be listed in
  `crates/core/src/bindings.rs`, or the file references a name it never declares. The drift test
  fails CI otherwise, which is why the formatter ignores that file (`.oxfmtrc.json`).
- Build `lcu` and `winer-core` on their own too (`cargo test -p lcu -p winer-core`, as CI does):
  in a whole-workspace build a reqwest feature the app turns on (`json`) is on for every crate.
- The shell embeds `plugin/dist/index.js` (`app/src-tauri/build.rs`): a release build without it
  panics, a debug build uses a stub. Run `pnpm build` first.
- It also embeds Pengu Loader's `core.dll` from `vendor/pengu-loader/`, a third-party binary that is
  injected into the client: replace it only from a signed upstream release, following that
  folder's README, and update the hash the `core_dll_is_the_vendored_release` test pins.

## Windows QA host (real hardware, over SSH)

```bash
ssh -F ~/.ssh/windows-local.conf windows-local
```

- The login shell is Windows PowerShell 5.1; use **`pwsh` 7** (UTF-8, no `#< CLIXML` wrapper)
  through `-EncodedCommand` (UTF-16LE base64), as `scripts/windows/qa.sh` does, so bash never
  interpolates `$`. For anything non-trivial use Python or Rust, both under mise; call the shim by
  full path (`C:\Users\Administrator\AppData\Local\mise\shims\python.exe`): `WindowsApps` comes
  first on `PATH` and a bare `python` is the Microsoft Store stub.
- **The host is elevated** (built-in Administrator, build 26100). It cannot prove anything about
  running without Administrator rights; the non-elevated facts in `docs/platform-notes.md` come
  from a different, non-elevated machine. Do not present an elevated run as evidence for them.
- **SSH runs in session 0**, where WebView2 cannot composite and session 1's windows are
  invisible to `EnumWindows` and `PrintWindow`. GUI work goes through
  `scripts/windows/run-in-session.ps1` (a scheduled task with `/IT` in the console session).
- **A human uses the console session.** Never inject input. Drive winer's own window over its
  WebView2 DevTools port instead (`qa.sh eval` / `shot`), and leave the client as you found it
  (`POST /riotclient/ux-minimize` if it was minimized).

### The QA loop

```bash
scripts/windows/qa.sh build        # cross-build with the `qa` feature
scripts/windows/qa.sh deploy       # copy, restart in session 1 with DevTools on 9333
scripts/windows/qa.sh shot <name> ['<js>']   # run the js in winer's window, then screenshot
scripts/windows/qa.sh eval '<js>'  # e.g. document.querySelector('h1').innerText
scripts/windows/qa.sh lcu GET /lol-gameflow/v1/gameflow-phase   # the token never leaves the host
scripts/windows/qa.sh log 40
```

- The `qa` cargo feature opens WebView2's DevTools port when `WINER_DEVTOOLS_PORT` is set. Any
  local process can then script the window: it is for this loop only and never in a release.
- `custom-protocol` is not optional for a Windows build: without it the frontend is not embedded
  and the window renders blank (every pixel rgb(45,45,45)).

### Live champ select: read this before creating a lobby

- **Nothing backs out of a custom champ select.** On ARAM all-random,
  `cancel-champ-select` answered 204 and did nothing, `DELETE /lol-lobby/v2/lobby` answered 404,
  and the timer running out launched the game (2026-10-05; the game server then refused
  `early-exit`, and killing the game left the client in `Reconnect` for four minutes).
- There is no scripted champ-select test that is known to end without a game. A draft custom
  lobby where nobody locks in should end by itself when the pick timer runs out, but that was
  never run. Whatever the mode: check the phase is `None` first, switch winer's pick and ban
  automation off, and ask the user before creating a lobby.
- Custom games give no rerolls. An all-random custom lobby does put the pool's extras on the
  bench, so the in-client bench swap can be exercised there, **but its timer always launches the
  game**: only with the user's consent, close the game (`League of Legends` process) when it
  starts, and expect the client in `Reconnect` for about four minutes. It was done that way on
  2026-10-05 with the user's agreement.
- To test a side, a custom lobby's player moves teams with the lobby's own 加入 button, clicked over
  the client page's debug port; the API refuses (`docs/platform-notes.md`). A lone red player reads
  `team: 2` in champ select.
- Driving the client page itself needs Pengu's `RemoteDebuggingPort` (see
  `docs/platform-notes.md`); show the client window first (`POST /riotclient/ux-show`), because a
  hidden page never runs the plugin's frame callbacks, and restore the port to `0` afterwards.

## Releases

- **One version, one place.** The root `package.json` holds the app's version; `tauri.conf.json`
  points at it (`"version": "../../package.json"`), `app/src-tauri/build.rs` hands it to the code as
  `WINER_VERSION`, and the plugin's banner reads it. The Cargo crates keep a static `0.0.0`, so a
  release never touches `Cargo.lock`. Never edit a version by hand: release-please owns it.
- **Every change lands through a pull request merged with squash**:
  `gh pr merge --squash --match-head-commit <verified head>`, never `--admin`, never a direct push
  to `main` (its ruleset takes changes through a pull request only, `CI Success` green). The PR title
  is a Conventional Commit (`feat: …`, `fix: …`): it becomes the squash subject and release-please
  reads it.
- **One change per version.** Merge one squashed change, then the release PR release-please opens
  (`chore: release X.Y.Z`), so `main` reads change, release, change, release. Related work goes
  into one PR rather than several merges before a release.
- **Patch numbers only before 0.1.0.** `release-please-config.json` sets
  `"versioning": "always-bump-patch"`, so every release adds one to the last number whatever the
  commits say. Moving to 0.1.0 is the owner's call: a `Release-As: 0.1.0` footer, then a new
  versioning rule.
- **What a release does.** Merging the release PR runs `.github/workflows/release.yml`: tag and
  draft, the Windows NSIS leg (`pnpm tauri build --no-bundle`, then `pnpm tauri bundle` with the
  signing key), every updater signature checked against the embedded public key, `latest.json`,
  `SHA256SUMS`, attestations, and the draft published only once every remote asset matches.
  `scripts/install.ps1` ships as an asset of the same release. A failed run is rebuilt with
  `workflow_dispatch` and the draft's tag; a published release is immutable, so a broken one means
  a new version.
- **The updater key** (key id `F9ABD555ED709F50`) signs every update; its private half is the
  repository secret `TAURI_SIGNING_PRIVATE_KEY` (password in `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`)
  and the owner's copy. Losing it strands every installed copy (`docs/updater-key-management.md`).

## Conventions a new session gets wrong

  convention.
- Rust uses rustfmt's defaults (no `rustfmt.toml`); TypeScript, JSON, YAML and Markdown use oxfmt
  (`pnpm format`).
